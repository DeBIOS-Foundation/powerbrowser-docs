## Capability gaps (no surface supports these yet)

- Read page DOM or page text from Theia or from an external agent. No actor kind or MCP tool returns page content. Building it requires a new store kind in `$PB_REPO/powerbrowser/shell/PowerBrowserAPI.sys.mjs`, plus a relay kind and MCP tool if agents need it, or a WebExtension that reports to a loopback listener.
- Open, close or navigate tabs from an external agent. MCP has no navigation tool and excludes `closeGroup`. Building it requires new tools plus chrome kinds that reach `openStockTab` and the web-tab kinds; `TAB_STORE_RELAY_KINDS` holds no web-tab kind and [03-tab-store-mcp-server.md](03-tab-store-mcp-server.md) says not to add one, so this is a PB core design change (see [Rules and constraints](03-tab-store-mcp-server.md#rules-and-constraints)).
- WebExtension UI in the Theia shell. Browser actions, popups and sidebars render only in stock windows. Building it requires shell chrome, which is blocked by rule 5 ("no custom browser chrome is authored").
- WebExtension access to PB tab and group data. There is no bridge: an add-on cannot read `tabs.sqlite` or the group model. Building it requires a native-messaging host or a loopback client of the MCP endpoint.
- WebExtension `tabs` view of in-shell web tabs (source present; the live behaviour is not yet checked). Phase 31.1 adds an extension tab host: patch `$PB_REPO/patches/050-extension-tab-host.patch` opens the extension tracker gate for the tab host window, and `PowerBrowserTabHost` in `$PB_REPO/powerbrowser/shell/PowerBrowserAPI.sys.mjs` gives each live web-tab overlay one tab node, with the Theia frame absent. UNVERIFIED: that `browser.tabs.query({})` lists the in-shell web tabs in a built PB. Verify: build PB with patch 050, then run `"$PB_REPO"/scripts/verify-platform.sh --only ext-tab-host-live` (checks in `$PB_REPO/scripts/verify-ext-tab-host-live.mjs`).
- A `powerbrowser.*` API namespace for `.vsix` plugins. The `extPluginApi` hook exists, but nothing is built and the design note is superseded.
- Theia exposed as an MCP server. `@theia/ai-mcp-server` is not a dependency in `$PB_REPO/theia/applications/browser/package.json`. Adding it at 1.76.0 is a PB core change.
- Theia AI using PB's own tab-store MCP endpoint. Port and token change on every start, so a static `mcpServers` entry goes stale. UNVERIFIED: that Theia AI can use the endpoint end to end. Verify: configure `ai-features.mcp.mcpServers` from the current `store-access.json` in a PB build and call a tab-store tool from chat. Building it requires an extension that rewrites the preference or registers tools from `store-access.json` at startup.
- Push events to external agents. The MCP endpoint has no SSE, no sessions and no change notifications, so clients must poll.
- Remote (non-loopback) access to any PB API. All listeners are loopback-only by design (SIDE-01).
- Passing a URL to a running instance. `PowerBrowserSingleInstanceHandler` drops all arguments when a shell window exists.
- Shipping unsigned add-ons. There is no key in `$PB_REPO/configuration.toml` for `xpinstall.signatures.required`.
- Runtime install of Theia-native extensions. Every `@powerbrowser/*` extension needs a PB rebuild.

Scope note: PB's planning files list "DSH (DeepSeek Harness) and any AI assistant integration" and "Customising Theia's AI framework" (stays stock until a later milestone, RM-02) as Out of Scope; at the stamped PB commit they sit in `$PB_REPO/.planning/PROJECT.md`, section "Out of Scope". UNVERIFIED: this scope decision rests only on PB planning files, which can lag. Verify: read `$PB_REPO/.planning/PROJECT.md` section "Out of Scope" at your PB HEAD and ask the user. Confirm with the user before shipping AI tools or agents into PB core.
